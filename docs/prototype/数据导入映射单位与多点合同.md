# 数据导入映射、单位与多点合同

日期：2026-07-10  
状态：字段映射、单位、真实点位与多点导入的 authoritative design baseline  
关联流程：`项目/点位数据 -> 数据导入 -> 数据检查`

## 1. 页面任务

数据导入页的任务不是证明文件已经上传，而是让用户把外部表格可靠地转成一个或多个可检查的点位草稿。

```text
选择文件
-> 解析文件结构
-> 核对字段映射
-> 核对单位
-> 查看标准化预览
-> 确认点位拆分计划
-> 生成点位导入草稿
-> 运行数据检查
```

三个决策必须属于同一个导入批次：

```text
SourceColumn[]
-> FieldMappingDecision[]
-> UnitDecision[]
-> NormalizedRow[]
-> PointSplitPlan
-> PointImportDraft[]
```

字段映射决定某列是什么，单位决定数值如何标准化，点位策略决定标准化数据交给哪些点位。这三层不能作为互不关联的页面提示。

## 2. 完整产品对象

### 2.1 ProjectWorkspace

```ts
type ProjectWorkspace = {
  projectId: string;
  projectName: string;
  workspaceRevision: number;
  points: PointWorkspace[];
  activePointId: string | null;
  importBatches: ImportBatchRecord[];
  activeImportBatchId: string | null;
};
```

项目是点位和导入批次的容器。项目本身不再直接拥有唯一的 `flowCase`、`importDraft` 和检查状态。

### 2.2 PointWorkspace

```ts
type PointWorkspace = {
  pointId: string;
  pointName: string;
  aliases: string[];
  importDrafts: PointImportDraft[];
  activeImportDraftId: string | null;
  checkState: CheckState;
  stratificationState: WorkflowArtifactState;
  parameterState: WorkflowArtifactState;
  outputState: WorkflowArtifactState;
  createdAt: string;
  updatedAt: string;
};
```

每个点位独立拥有导入、检查和后续流程状态。切换点位时，页面读取该点位的状态，不能共享上一个点位的检查结果。

`activePointId`、`activeImportBatchId` 和 `activeImportDraftId` 始终保存不可变 ID。点位名称只用于显示，重命名不能改变关联关系。

### 2.3 ImportBatchDraft

```ts
type ImportBatchRecord = ImportBatchDraft | ImportBatchTombstone;

type ImportBatchDraft = {
  kind: 'draft';
  batchId: string;
  operationId: string;
  baseWorkspaceRevision: number;
  sourceFingerprint: string;
  source: ImportSource;
  parseState: 'selected' | 'parsing' | 'parsed' | 'error';
  workflowState:
    | 'editing'
    | 'ready-to-generate'
    | 'generating'
    | 'generated'
    | 'partially-generated'
    | 'failed'
    | 'cancelled';
  sourceColumns: SourceColumn[];
  rawDataBlockId: string | null;
  mappings: FieldMappingDecision[];
  unitDecisions: UnitDecision[];
  normalizedDataBlockId: string | null;
  pointPlan: PointSplitPlan;
  problems: ImportProblem[];
  generatedDraftIds: string[];
  revisions: {
    source: number;
    mapping: number;
    unit: number;
    normalization: number;
    pointPlan: number;
  };
  createdAt: string;
  updatedAt: string;
};

type ImportBatchTombstone = {
  kind: 'tombstone';
  batchId: string;
  sourceFingerprint: string;
  sourceSummary: { fileName: string; fileType: string; rowCount: number };
  revisions: RevisionVector;
  generatedDraftIds: string[];
  archivedAt: string;
};
```

导入批次保存用户的决策过程。重新上传文件可以替换当前批次，也可以新建批次；取消分支决策不能破坏已经存在的点位草稿。

原始文件字节和行数据不直接写入 `localStorage`。权威项目清单、引用和不可变行数据块统一进入 IndexedDB `ImportDataStore`，在同一个事务中提交；`localStorage` 只保存数据库版本和启动指针，不作为项目真源。一个标准化数据块只保存一次，点位草稿通过稳定行引用读取，避免批次和多个点位重复保存整份数据。

启动时必须忽略孤立的非权威指针，并以 IndexedDB 已提交事务为准。数据块通过点位草稿和成果依赖的可达性引用计数回收，不能在仍有引用时删除。

解析与页面预览使用非持久化 `ImportBatchWorkingSet`，按 data block ID 从 `ImportDataStore` 读取 `rawRows/normalizedRows`。Working Set 可以缓存当前批次行数据，但不进入 V2 manifest/schema；manifest 中只有 block ID、列摘要、决策、问题和版本。

异步解析结果只有在 `operationId` 仍是当前活动操作且 `baseWorkspaceRevision` 未过期时才能写回。连续选择两个文件时，较慢的旧解析结果必须被丢弃。

### 2.4 SourceColumn

```ts
type SourceColumn = {
  columnId: string;
  sourceIndex: number;
  header: string;
  normalizedHeader: string;
  sampleValues: string[];
  inferredValueType: 'text' | 'number' | 'mixed' | 'empty';
  mappingCandidates: MappingCandidate[];
};
```

`columnId` 由批次、`sourceRevision` 和列序号产生，不能用表头作为唯一键，因为文件可能包含重名表头，替换文件后也不能复用旧列身份。

### 2.5 FieldMappingDecision

```ts
type TargetFieldKey =
  | 'pointName'
  | 'depthM'
  | 'qc'
  | 'qt'
  | 'fs'
  | 'u2'
  | 'fr'
  | 'waterDepth'
  | 'finalDepth';

type FieldMappingDecision = {
  targetField: TargetFieldKey;
  sourceColumnId: string | null;
  requiredLevel: 'required' | 'recommended' | 'optional';
  decisionSource: 'auto-exact' | 'auto-alias' | 'user' | 'unmapped';
  suggestionSource: 'standard-header' | 'alias-dictionary' | 'value-shape' | 'none';
  confidence: 'high' | 'medium' | 'low' | 'none';
  state: 'candidate' | 'confirmed' | 'missing' | 'conflict';
  confirmedAt?: string;
  confirmedRevision?: number;
};
```

规则：

- 自动精确匹配可以直接进入 `confirmed`，但页面仍允许修改。
- 中低置信度、多个候选或表头含义不明时进入 `candidate`。
- 必需目标字段未映射时进入 `missing`，不能运行数据检查。
- 同一个源列不能同时映射到两个互斥目标字段；冲突时两项都进入 `conflict`。
- 用户可以清除、修改、确认单项，也可以重置为自动建议。
- 修改映射必须增加 `mappingRevision`，并重新生成单位建议、标准化预览和导入问题。
- `pointName` 是条件必需字段：可以来自源列，也可以由明确的点位归属决策提供，不能用隐藏默认值补齐。

### 2.5.1 点位归属来源

```ts
type PointAttributionDecision =
  | { source: 'source-column'; sourceColumnId: string }
  | { source: 'constant-name'; pointName: string }
  | { source: 'existing-point'; pointId: string };
```

当文件没有点位列时，用户输入固定点位名称或选择已有点位后，`PointName` 缺映射问题才能关闭。系统据此为所有源行生成同一个 `detectedPointKey`，并在 provenance 中记录归属来源。

### 2.6 UnitDecision

```ts
type UnitDecision = {
  targetField: TargetFieldKey;
  sourceColumnId: string;
  detectedUnit: string | null;
  selectedUnit: string | null;
  standardUnit: 'm' | 'kPa' | '%' | 'text';
  decisionSource: 'header' | 'value-range' | 'user' | 'not-applicable';
  confidence: 'high' | 'medium' | 'low' | 'none';
  state: 'confirmed' | 'needs-confirmation' | 'conflict' | 'not-applicable';
  conversion: { scale: number; offset: number } | null;
};
```

允许的首批单位：

| 目标字段 | 可选源单位 | 标准单位 |
| --- | --- | --- |
| 深度、水深、最终孔深 | `m`、`cm`、`mm` | `m` |
| qc、qt、fs、u2 | `kPa`、`MPa` | `kPa` |
| Fr | `%`、小数比值 | `%` |
| 点位编号 | 不适用 | text |

确定性换算：

| 源单位 | 标准单位 | scale | offset |
| --- | --- | ---: | ---: |
| `m` | `m` | 1 | 0 |
| `cm` | `m` | 0.01 | 0 |
| `mm` | `m` | 0.001 | 0 |
| `kPa` | `kPa` | 1 | 0 |
| `MPa` | `kPa` | 1000 | 0 |
| `%` | `%` | 1 | 0 |
| 小数比值 | `%` | 100 | 0 |

规则：

- 表头明确写出支持单位时，可自动确认并允许用户修改。
- 仅凭值域猜测时只能产生候选，必须显示推断依据并由用户确认；值域不能自动确认单位。
- 单位未确认时可以查看原始数据，但不能生成最终标准化草稿或运行数据检查。
- 同一源列不能在行级混用单位；检测到混合文本单位时标记问题。
- 修改单位后重新标准化全部受影响行，并使对应点位的旧检查及后续结果失效。
- 页面必须同时显示源值、源单位、标准化值和标准单位，不能只显示换算后结果。
- 内部保存完整有限数值，不在换算时做显示舍入；表格默认深度显示 3 位小数、压力显示 2 位小数、Fr 显示 3 位小数。`NaN`、`Infinity` 和溢出值均形成问题，不能进入数据块。

### 2.7 PointSplitPlan

```ts
type PointSplitPlan = {
  detectedPoints: DetectedPoint[];
  selectedPointKeys: string[];
  strategy: 'single' | 'split-all' | 'split-selected' | 'pending' | 'cancelled';
  conflicts: PointTargetDecision[];
  executions: PointExecutionRecord[];
  state: 'ready' | 'needs-decision' | 'conflict' | 'cancelled';
};
```

```ts
type PointTargetDecision = {
  detectedPointKey: string;
  targetAction: 'create-point' | 'replace-active-draft' | 'keep-as-new-draft' | 'create-renamed-point' | 'skip';
  targetPointId?: string;
  proposedPointName: string;
  state: 'ready' | 'needs-decision';
};

type PointExecutionRecord = {
  detectedPointKey: string;
  status: 'pending' | 'generated' | 'skipped' | 'problem' | 'failed';
  idempotencyKey: string;
  sourceFingerprint: string;
  resultPointId?: string;
  resultDraftId?: string;
  errorCode?: string;
};
```

规则：

- 文件只有一个点位且名称不冲突时，计划自动为 `single`。
- 文件有多个点位时，默认建议“拆分全部点位”，用户也可只选择部分点位或取消。
- 文件缺少点位列时，用户必须输入点位名称或选择一个已有点位。
- 与已有点位同名时不能静默覆盖，必须逐点选择：替换活动草稿、保留为同点位新草稿、另存为重命名点位或跳过。
- `normalizedPointKey` 使用去除首尾空白、统一大小写和规范化连续空白后的值；点位名称和 aliases 在同一项目内共同唯一。生成前必须基于最新 `workspaceRevision` 再检查一次冲突。
- 行内空点位值单独形成问题，不能自动继承前一行点位。
- 多点文件按点位分别验证深度递增和最终孔深，不能跨点位比较相邻行。
- 取消点位计划只取消本次批次生成动作，不删除已有点位和既有草稿。

### 2.8 PointImportDraft

```ts
type PointImportDraft = {
  draftId: string;
  batchId: string;
  pointId: string;
  pointName: string;
  sourceRowIds: string[];
  dataBlockId: string;
  valueProvenance: Record<TargetFieldKey, ValueProvenance>;
  revisions: RevisionVector;
  problems: ImportProblem[];
  status: 'ready' | 'issue' | 'stale';
};
```

同一批次生成的点位草稿共享映射和单位决策来源，但分别保存稳定行引用、问题和下游状态。`sourceRowId` 同时关联零基内部索引和一基用户可见文件行号，页面和测试统一显示后者。

`ValueProvenance` 必须区分 `source`、`derived`、`defaulted` 和 `missing`。例如缺少 qt 时不能悄悄把 qc 当作 qt；如果允许派生或替代，必须由明确规则生成并在检查页保留来源。默认值不能伪装成文件原始值。

### 2.9 数据块与依赖状态

```ts
type RevisionVector = {
  source: number;
  mapping: number;
  unit: number;
  normalization: number;
  pointPlan: number;
};

type ArtifactDependency = {
  pointId: string;
  draftId: string;
  batchId: string;
  revisions: RevisionVector;
};

type WorkflowArtifactState = {
  status: 'empty' | 'current' | 'stale' | 'problem';
  input: ArtifactDependency | null;
  staleReason?: string;
  invalidatedAt?: string;
  recoveryTarget?: { route: string; field?: TargetFieldKey; reasonCode?: string };
};

type CheckRun = {
  runId: string;
  input: ArtifactDependency;
  status: 'running' | 'completed' | 'failed';
  counts: { issue: number; notice: number; passed: number };
  conclusion: '无问题' | '存在问题';
  issueIds: string[];
  createdAt: string;
  completedAt?: string;
};

type CheckState = {
  activeRunId: string | null;
  runs: CheckRun[];
  legacyHistory: LegacyCheckRunSummary[];
  artifact: WorkflowArtifactState;
};
```

检查、分层、参数和成果都保存自己的输入依赖快照。是否失效通过依赖向量比较得到，不能只比较一个项目级数字。

每个 V2 `CheckRun` 必须绑定完整 `ArtifactDependency`。V1 记录只有在 `checkedDraftVersion` 能唯一对应迁移后的活动草稿时，才可生成带初始 RevisionVector 的 V2 run；无法证明对应关系的记录进入只读 `legacyHistory`，`artifact.status = stale`，并提供重新检查动作。

### 2.10 草稿生成事务

多点草稿生成采用“先计划、后一次提交”的两阶段方式：

```text
配置映射/单位/点位目标
-> 预览将创建、替换、跳过的结果
-> 用户确认
-> 一次性生成所选且就绪的点位草稿
```

- 确认前不修改项目点位集合。
- 用户本次选中的全部就绪点位作为一个 IndexedDB 事务：任一写入失败时全部回滚本次新增和替换，保留导入批次供用户重试。
- “只生成无问题点位”必须是用户明确选择，未选中的问题点继续保留在批次中。
- 取消只改变本批次状态，不删除已存在点位、活动草稿或检查记录。
- 批次生成后保留 `generatedDraftIds`，用于追溯每个点位草稿的来源。
- 每个点位计划保存执行记录：`pending / generated / skipped / problem / failed`、`resultPointId`、`resultDraftId` 和 `sourceFingerprint`。事务提交成功后才把本次选中项统一改为 `generated`；存储失败时这些项统一回到 `failed` 或 `pending`，项目集合没有部分写入。
- `partially-generated` 只表示用户明确跳过或暂不选择了某些问题点，同时其余选中点已经完整提交；它不表示存储事务只成功了一部分。
- 提交命令携带 `baseWorkspaceRevision` 和稳定幂等键；同一批次重试只能处理尚未生成项，不能重复创建已成功点位。
- 替换活动草稿时同时校验 `expectedActiveDraftId`，避免覆盖用户在另一个操作中刚切换的草稿。
- 已生成草稿若尚未产生新的下游结果，可以从批次记录撤销；已有下游结果时，转到点位删除或草稿替换确认流程处理。

### 2.11 批次生命周期

```text
editing
-> ready-to-generate
-> generating
-> generated | partially-generated | failed

editing / ready-to-generate -> cancelled
generated / partially-generated -> reopened -> editing
```

- 项目保留批次列表，支持打开、切换、重命名备注、重新打开、删除未生成批次和查看已生成批次来源。
- 未生成且未被引用的批次可以删除。已被草稿或成果引用的批次只能转换为不可编辑 `ImportBatchTombstone`，保留 `batchId`、source fingerprint、修订向量、生成草稿引用和来源摘要，不能物理删除或制造悬空引用。V2 schema、迁移和引用校验必须识别两种 `ImportBatchRecord`。
- 同一点位新增草稿后默认切换到新草稿；旧检查仍绑定旧草稿只读保留，新活动草稿显示“未检查”。
- 切换活动草稿会立即按该草稿依赖重新判断检查及后续状态。

### 2.12 V1 到 V2 迁移合同

V1 是当前 `localStorage` 单项目单点结构；V2 是 IndexedDB 中的项目清单、点位聚合、批次和数据块结构。

迁移顺序：

```text
读取并保留 V1 原文
-> 校验 V1
-> 构造确定性 V2 对象和数据块
-> 在一个 IndexedDB transaction 写入 manifest + blocks + migration record
-> 重新读取并按 V2 schema 校验引用
-> 写入 localStorage 启动指针
-> 标记迁移完成
```

任何一步失败时：

- 回滚未提交的 V2 transaction。
- 保留 V1 原文和原 key，不触发空集合自动保存或清除。
- 页面显示迁移问题，提供“重试迁移”和经过确认的“重置本机项目”。
- 未来版本快照同样暂停自动保存，不能按损坏数据处理。

确定性迁移表：

| V1 来源 | V2 目标 | 规则 |
| --- | --- | --- |
| `projectId/projectName` | ProjectWorkspace | 保留 ID 和名称，`workspaceRevision = 1` |
| `flowCase.point` | PointWorkspace | 保留非空 `pointId`；缺失时由 `projectId + normalizedPointKey` 哈希产生 |
| `importDraft + flowCase.rows` | ImportBatchDraft + data block | batch ID、block ID 由 `projectId + source file + draft version + content hash` 产生 |
| `importDraft` | PointImportDraft | draft ID 由 `pointId + batchId + content hash` 产生，保存完整初始 RevisionVector |
| `checkedDraftVersion/checkRunHistory` | CheckState | 绑定迁移后的 draft ID；无法证明版本对应时标为 stale，并给出重新检查动作 |
| `selection.selectedPointId` | `activePointId` | 名称值先解析到迁移点位 ID，无法解析时选择唯一点位或置空 |
| 分层、参数、成果样例状态 | WorkflowArtifactState | 只有可证明输入依赖时迁移为 current，否则迁移为 stale/empty，不伪造依赖 |

迁移记录保存原 V1 SHA-256、目标 V2 manifest ID、迁移器版本、时间和结果。V1 原文至少保留到一次成功加载并校验 V2 后；清理旧备份必须是独立、可确认的维护动作。

## 3. 用户动作与功能模块

| 用户动作 | 对象变化 | 必要功能 | 下一步 |
| --- | --- | --- | --- |
| 选择 CSV/Excel | 创建导入批次 | 文件选择、格式识别、解析状态 | 查看源字段 |
| 替换文件 | 批次版本增加 | 替换确认、旧决策失效 | 重新映射 |
| 选择目标字段 | 更新映射决策 | 字段下拉、候选与样例值 | 单位建议刷新 |
| 清除映射 | 目标字段变为未映射 | 清除、重置自动建议 | 处理缺字段 |
| 确认或修改单位 | 更新单位决策 | 单位选择、换算预览 | 生成标准化行 |
| 查看问题 | 选择问题定位 | 字段/行定位、问题筛选 | 修正决策或文件 |
| 选择点位策略 | 更新拆分计划 | 全部/部分选择、草稿数量预览 | 处理重名 |
| 处理点位重名 | 更新目标决策 | 替换/新增草稿/重命名/跳过 | 生成草稿 |
| 取消导入 | 批次取消或保留待处理 | 取消确认、返回 | 保留既有状态 |
| 运行数据检查 | 消费点位草稿 | 可检查性判断、版本记录 | 数据检查页 |

唯一可检查判定：

```text
canRunDataCheck(pointDraft) =
  pointDraft.status == ready
  AND all required source-backed mappings are confirmed
  AND all mapped numeric fields have confirmed units
  AND point attribution is ready
  AND point draft is the active draft of its point
  AND no issue-level problem remains for that point
  AND referenced data block exists
```

任一条件不满足时，页面必须给出准确问题和恢复位置，不能只返回 `false`。

`required source-backed mappings` 不包含已经由 `constant-name` 或 `existing-point` 归属决策满足的 `pointName`。归属进入 ready 后，`pointName` 映射状态从门禁集合中移除，但仍保留为“由归属决策提供”的 provenance；深度、qc 和最终孔深等数值必需字段仍必须来自已确认源列。

## 4. 页面承接

### 4.1 左侧固定导航

- 显示当前项目和当前点位。
- 显示六步工作流，不放字段或单位工具。
- 多点草稿生成后，点位切换器显示真实点位集合及各自状态。

### 4.2 中间工作区

按用户决策顺序组织，不把所有信息同时置于第一视觉层：

1. `First Look`：当前批次状态、最重要问题和唯一首要动作。
2. `源文件与字段映射`：源列、样例值、目标字段、映射状态。
3. `单位与标准化预览`：源值和标准化值并列，显示换算依据。
4. `点位计划`：识别点位、行数、深度范围、目标动作和问题。
5. `导入问题`：按问题/提示分组，并能定位到对应字段、单位或点位。

映射和单位使用紧凑表格或配置行，保持 Mixpanel 查询构建器式的高密度、即时反馈和逐项确认，不做大卡片说明区。

### 4.3 右侧页面功能区

右侧默认展开且可隐藏，只承接当前选择对象的操作：

- 未选择字段：批次摘要、模板、重置和取消。
- 选择源字段：样例值、目标字段选择、候选原因、映射确认。
- 选择数值字段：源单位选择、标准单位、换算样例、确认状态。
- 选择点位：目标点位动作、名称编辑和冲突处理。

右侧不重复中间完整表格；多点批量选择与最终拆分确认放在中间工作区或对话框。

### 5.1 与既有异常编号的对应关系

用户界面和已有测试继续显示稳定的 `DI-E` 编号；`DI-M/DI-U/DI-P/DI-X` 用于细分领域状态和新增测试名。

| 既有事件 | 细分事件 |
| --- | --- |
| `DI-E05` 至 `DI-E09` 字段问题 | `DI-M01` 至 `DI-M06` |
| `DI-E10` 点位不一致 | `DI-P02`、`DI-P04`、`DI-P05` |
| `DI-E11` 多点文件 | `DI-P03`、`DI-P06`、`DI-P07`、`DI-P08` |
| `DI-E15` 单位不明确 | `DI-U01` 至 `DI-U06`；未确认时禁止生成草稿和运行检查 |
| `DI-E16` 检查失效 | `DI-M06`、`DI-U06`、`DI-X04` |
| `DI-E18` 从检查返回 | `DI-X04` |

页面问题对象同时保存稳定 `eventId` 和细分 `reasonCode`，避免一个用户可见编号被误当成单一技术原因。

## 6. 状态失效规则

| 变化 | 直接重算 | 失效范围 |
| --- | --- | --- |
| 替换源文件 | 源列、映射建议、单位建议、点位计划 | 受影响批次生成的全部检查、分层、参数、成果 |
| 修改字段映射 | 单位建议、标准化行、问题、点位计划 | 受影响点位的检查及后续全部结果 |
| 修改单位 | 标准化行、问题、点位草稿版本 | 受影响点位的检查及后续全部结果 |
| 修改点位拆分选择 | 点位草稿集合 | 新增/移除点位对应的下游结果 |
| 替换点位活动草稿 | 检查输入版本 | 该点位检查、分层、参数和成果 |
| 点位重命名 | 导航和成果标签 | 数值检查不失效；成果元数据需要刷新 |
| 只修改批次备注 | 无 | 不使下游结果失效 |

任何失效状态都必须显示原因和恢复动作。页面不能只改变状态颜色而不给出“返回哪里、做什么、然后如何恢复”。

版本递增规则：

| 事件 | 递增修订 | 重新计算 |
| --- | --- | --- |
| 选择或替换源文件 | source | 源列、全部候选、原始行引用 |
| 修改字段映射 | mapping | 单位候选、标准化、点位计划、问题 |
| 修改单位 | unit | 标准化、点位计划、问题 |
| 标准化结果变化 | normalization | 数据块、逐点摘要 |
| 修改点位归属或拆分目标 | pointPlan | 点位执行计划 |

检查运行绑定 `pointId + draftId + batchId + RevisionVector`。恢复为 current 的唯一方式是用活动草稿的当前依赖重新运行；旧检查历史只读保留。

## 7. 实施阶段

### Stage A：聚合根、快照迁移与存储边界

- `ProjectWorkspace` 先迁移为真实 `points[] + activePointId + importBatches[]`，旧单点结构只作为 V1 迁移输入。
- 建立显式项目/点位/批次 reducer action，禁止通用 updater 改变实体 ID。
- 建立 `V1 -> V2 -> current validation` 解码管线；旧版、未来版或损坏快照加载失败时暂停自动保存并保留原始数据，只有用户明确重置后才能删除。
- 小型清单进入版本化快照，行数据进入 IndexedDB `ImportDataStore`，并验证引用完整性。
- 先用兼容适配器保持现有单点页面行为，再迁移页面读取新的活动点位。

### Stage B：导入领域层

- 从 `App.tsx` 提取 CSV 解析、源列分析和问题生成。
- 建立 `SourceColumn`、`FieldMappingDecision`、`UnitDecision` 和标准化纯函数。
- 解析行先获得稳定 `sourceRowId`，再按 `detectedPointKey` 分组进行深度、最终孔深和问题检查，禁止跨点位比较深度。
- 用单元测试覆盖映射冲突、单位换算、点位归属、逐点验证、幂等提交和异步旧结果丢弃。

### Stage C：单点映射与单位交互

- 中间表格允许选择和清除目标字段。
- 右侧功能区允许确认源单位，并即时显示标准化样例。
- 必需映射或单位未确认时禁用数据检查。
- 从数据检查返回时准确聚焦字段或单位。

### Stage D：多点导入

- 按 `PointName` 分组并分别检查深度。
- 实现全部/部分点位选择和草稿计划。
- 实现已有点位重名的逐点处理。
- 生成多个真实点位草稿并支持切换。
- 生成后的活动点位设为本次计划中的第一个生成项；默认只运行当前点位检查，点位列表提供逐点检查入口，批量检查另立后续功能合同。
- 部分生成时，无问题点位可逐点检查，问题点位留在批次并显示“返回修正”。

### Stage E：跨页失效闭环

- 映射、单位、文件和活动草稿版本统一进入依赖判断。
- 数据检查、地层分层、参数解译、成果输出显示准确失效原因。
- 恢复动作返回数据导入的具体字段、单位或点位。

### Stage F：Excel

- 接入浏览器端结构化解析库。
- 支持 Sheet 选择、表头行选择和与 CSV 相同的映射/单位/点位流程。
- Excel 不建立第二套业务对象。

## 8. Playwright 人类 Flow

所有案例在测试运行时生成文件，不依赖固定样例数据。

### FLOW-IMPORT-01：别名映射与 MPa 单位

```text
新建随机项目
-> 上传带别名表头和 MPa 数据的 CSV
-> 确认 qc 目标字段
-> 确认 MPa
-> 核对标准化为 kPa 的样例
-> 运行数据检查
```

证明：源值、标准化值、映射来源、单位决策和检查版本一致。

### FLOW-IMPORT-02：缺字段后手动恢复

```text
上传没有标准 DepthM 表头但包含深度数据的 CSV
-> 看见必需字段问题
-> 将未知源列映射到深度
-> 确认 m
-> 问题消失
-> 运行数据检查
```

证明：不是重新生成一份正确文件绕开问题，而是在页面内完成映射恢复。

### FLOW-IMPORT-03：单位歧义与检查失效

```text
上传无单位 qc 文件
-> 选择 MPa
-> 运行检查
-> 返回导入改为 kPa
-> 看见旧检查失效
-> 重新检查
```

证明：版本变化、失效原因和恢复路径完整。

### FLOW-IMPORT-04：三点拆分与重名处理

```text
项目已有一个随机点位
-> 上传包含三个点位的随机 CSV，其中一个重名
-> 选择拆分全部
-> 重名点选择保留为新草稿
-> 另外两点创建新点位
-> 生成三个点位草稿
-> 记录 B/C 的 canonical point state
-> 只对点位 A 运行数据检查
-> 切换 B/C 并核对状态完全未变
```

证明：项目点位数量、每点精确行数、活动草稿 ID 和依赖向量正确；A 的检查运行不会改变 B/C 的检查历史及后续状态。

### FLOW-IMPORT-05：取消不破坏既有状态

```text
已有可检查点位草稿
-> 上传多点文件
-> 在拆分确认中取消
-> 返回原点位
```

证明：除新候选批次的 `workflowState = cancelled` 外，原项目 canonical snapshot 深度相等。

### FLOW-IMPORT-06：部分点位存在问题

```text
上传三点文件，其中一点评价深度倒序
-> 查看逐点摘要
-> 只生成两个无问题点位草稿
-> 修正文件后重新上传问题点
```

证明：问题隔离在对应点位，其他点位不会被错误禁用。

### FLOW-IMPORT-07：映射歧义与重复冲突

```text
上传同时包含 Qc、ConeResistance 和 UnknownDepth 的随机 CSV
-> 查看 qc 多候选问题
-> 选择 Qc
-> 故意把同一源列再映射到 qt
-> 看见重复映射问题且检查禁用
-> 清除冲突并确认
```

证明：候选、冲突、恢复动作和 mappingRevision 均由真实操作产生；每次已提交映射修改恰好增加一次 revision，取消编辑不增加，最终检查按钮恢复启用。

### FLOW-IMPORT-08：不支持或混合单位

```text
参数化案例 A：上传含 psi 表头的随机 CSV
-> 定位单位或问题行
-> 确认无法直接检查
-> 替换为修正文件
-> 确认单位并恢复

参数化案例 B：上传同列混合 kPa/MPa 文本的随机 CSV
-> 定位全部冲突行
-> 确认无法直接检查
-> 替换为统一单位文件
-> 确认单位并恢复
```

证明：错误文件不能通过手动点一下“继续”绕过，修正后源 fingerprint 和单位版本更新。

### FLOW-IMPORT-09：缺点位归属与替换取消

```text
已有活动点位和检查记录
-> 上传没有 PointName 的随机 CSV
-> 选择归属到已有点位
-> 在替换活动草稿确认中取消
-> 再选择保留为同点位新草稿
```

证明：第一次取消保持活动草稿和检查不变；第二次生成新草稿并将旧检查保留为只读历史。

### FLOW-IMPORT-10：解析失败、重试和旧操作竞争

```text
选择一个故意延迟解析的文件 A
-> 立即选择文件 B
-> B 成为活动批次
-> A 的迟到结果被忽略
-> 通过一次性故障注入使 B 的第一次标准化失败
-> 对同一 B 执行重试并成功
```

测试使用可控解析 barrier 暂停 A，等待 B 建立 operation 后再释放 A，不依赖任意 sleep。B 使用仅第一次触发的确定性 failpoint。证明：A 没有任何写回；B 重试复用 sourceFingerprint 和幂等键；批次、点位和草稿 ID 集合无重复。

## 9. 验收证据

每个 Flow 至少产出：

- 测试运行时生成的输入文件。
- 关键决策前后截图，覆盖 `1440x900`；核心页面补充 `1920x1080`。
- `flow-run.json`：步骤、批次、映射、单位、点位计划和最终状态。
- `parsed-import-result.json`：源列、标准化行摘要和逐点行数。
- 浏览器 console/page error 记录。
- 横向溢出、右侧功能区遮挡和文本溢出检查。

证据必须先由断言证明，再写入 JSON，不能在测试中写死“通过”数字：

- 测试生成器返回精确 oracle：源列、每列单位、标准化样例、点位数、逐点行数和预期问题。
- 页面可观察值与 oracle 逐项 `expect` 相等后，才写入 `flow-run.json`。
- 证据记录 source SHA-256、批次 ID、修订向量、完整映射/单位决策、逐点草稿 ID、检查输入依赖和 before/after 状态摘要。
- 定义 `canonicalExistingWorkspaceSnapshot`：排除本次新候选批次，去除 `updatedAt` 和瞬时 UI 选择后，序列化全部既有项目、点位、草稿、问题、检查历史，以及检查/分层/参数/成果四级依赖状态。取消案例分成两个断言：既有 workspace 的 `after` 与 `before` 深度相等；新候选批次除 `workflowState: editing -> cancelled` 外，其余 canonical 内容深度相等。
- 跨页失效必须分别覆盖文件、映射、单位和草稿切换，并在数据检查、地层分层、参数解译、成果输出验证准确原因。
- Excel 验收使用测试运行时生成的真实 XLSX 工作簿，不能使用改扩展名的占位文本。
- 普通测试产物写入 `testInfo.outputPath()`；只有设置里程碑证据开关且全部断言通过后，才提升代表性 seed 到 `process_logs/playwright-mcp/`。

失败条件：

- 用户没有确认低置信度映射或单位却可以运行检查。
- 多点文件被写入单个点位草稿。
- 取消操作改变了既有点位或检查状态。
- 修改映射或单位后仍可使用旧检查继续进入地层分层。
- 页面声称已生成多个点位，但项目/点位数据页无法切换并读取独立状态。
- Playwright 只断言元素存在，没有完成真实上传和决策动作。

## 10. 首个编码切片

合同通过复查后，先实施 `Stage A + Stage B`：

```text
真实点位聚合根与 V1 -> V2 迁移
+ IndexedDB 行数据边界
+ 导入批次/映射/单位/点位纯领域模型
+ 逐点解析与版本依赖
```

完成这一基础后进入 `Stage C` 的单点可编辑映射与单位确认。不能继续把映射和单位临时计算在 React 渲染函数中，也不能先把新交互绑在旧项目级唯一 `ImportDraft` 上。多点 UI 在 `Stage D` 出现，但 Stage B 的领域函数必须已经支持按点位分组。
