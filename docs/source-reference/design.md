# Design Contract

日期：2026-07-03

适用范围：`OffshoreGeotechWorkbench` 的 UI 设计、Figma 图稿、页面重排、弹窗/面板设计和后续 WinUI 实现 handoff。

本文只保存稳定规则：统一布局、统一色彩、统一排版密度、设计工作流、功能入口闭环、agent 审阅闭环。具体页面历史、临时反馈、截图记录、过程讨论放入 `docs/*review.md`、`docs/*plan.md` 或 `process_logs/`，不得塞回本文。

## 0. 强制执行摘要

任何 UI/Figma/页面 handoff 任务必须先过以下 gate。缺失任一 gate 时，设计只能标为 `draft`，不得进入开发 handoff 或代码实现。

1. Scope gate：每轮只处理一个页面、一个区域或一组强相关弹窗；批量页面只能作为探索草稿，不得直接 handoff。
2. Product gate：先写清当前对象、输入、主结果、状态/阻断、下一步、详情/日志位置。
3. Template gate：主流程页必须从已验收 `01 Workbench shell` 或已验收同类页面复制壳层；不得重新手绘“相似壳层”。
4. Layout gate：必须和已验收 `01/03/04` 版型做区域对照，证明 Top chrome、ActivityBar、Explorer、Tabs、Editor、RightPanel、BottomPanel、StatusBar 坐标/职责/密度一致。
5. Feature gate：每个新增按钮、菜单、节点或入口都必须说明落点、状态、失败态、禁用原因，以及是否改写数据对象。
6. User gate：中文工程用户只看首屏 10 秒，应能说出“我在哪、结果是什么、下一步点哪里”；否则为 `blocking`。
7. Review gate：Planning、UI/layout、Chinese user critique、Implementation/QA 审阅必须完成；agent 不可用时只能标为 `blocked for review`，不能写 `pass`。
8. Handoff gate：只有通过以上 gate 的 Figma 节点才能进入 `development-handoff`。Figma 同步、截图导出、自检通过都不等于验收通过。

当前优先单页循环顺序固定为：

```text
05 地层分层默认页 -> 05B 地层分层方法选择器 -> 06 参数解译默认页 -> 06A 参数方法选择器 -> 07 成果输出 -> 02 项目/点位数据
```

`08 方法实验室`、`09 研究模式` 只能作为高级入口草稿；`10 全局状态集` 只能作为设计/QA 状态规范画板，不得进入用户主流程。

## 1. 固定方向

当前 UI 方向锁定为：

```text
VSCode-like 工程工作台
```

主流程固定为：

```text
项目/点位数据 -> 数据导入 -> 数据检查 -> 地层分层 -> 参数解译 -> 成果输出
```

默认用户是中文工程/科研使用者。默认界面必须先回答：当前数据是什么、结果是什么、状态是否可继续、下一步做什么。不得让用户先读内部日志、runner、registry、draft package、trace 或长说明才能理解页面。

## 2. 统一布局

所有主流程页必须继承同一套工作台壳层，不允许每页自由重画。

统一基准：

| 项 | 基准 |
| --- | --- |
| Figma 文件 | `Untitled` |
| 基准 Frame | `01 Workbench shell` |
| 基准节点 | `1:408` |
| 基准截图 | `app_data/temp/figma-01-workbench-shell-after-fix.png` |
| 验收尺寸 | 1920 x 1080 full frame |

统一区域与尺寸：

| 区域 | 坐标与尺寸 | 是否可变 |
| --- | --- | --- |
| `WorkbenchTopChrome` | x0 y0 w1920 h36 | 不可漂移，只替换当前标题/状态文案 |
| `ActivityBar` | x0 y36 w48 h1020 | 不可漂移，只变更选中状态 |
| `ExplorerPane` | x48 y36 w300 h1020 | 不可漂移，树内容可按当前流程变化 |
| `Tabs` | x348 y36 w1252 h36 | 不可漂移，Tab 项可变化 |
| `EditorArea` | x348 y72 w1252 h794 | 主要业务内容可变化 |
| `RightPanel` | x1600 y36 w320 h1020 | 壳层不可漂移，属性内容可变化 |
| `BottomPanel` | x348 y866 w1252 h190 | 壳层不可漂移，问题/预检/摘要内容可变化 |
| `StatusBar` | x0 y1056 w1920 h24 | 不可漂移，只替换状态文案 |

主流程页新增设计时，必须复制已验收的 `01 Workbench shell`，只替换 `EditorArea`、`RightPanel` 内容、`BottomPanel` 内容和必要状态文案。若没有直接复制壳层，必须做坐标/尺寸一致性检查。

## 3. 统一色彩

当前色彩系统固定为 VSCode-like 浅色工程工作台。

基础 token：

| Token | Hex | 用途 |
| --- | --- | --- |
| `VSCodeActivityBar` | `#333333` | 左侧深色活动栏 |
| `VSCodeTitleBar` | `#DDDDDD` | 顶部应用栏/标题栏 |
| `VSCodeSideBar` | `#F3F3F3` | Explorer、右侧面板、浅灰区域 |
| `VSCodeEditor` | `#FFFFFF` | 中央编辑区与表格主体 |
| `VSCodeLine` | `#E5E5E5` | 分隔线、表格线、边界线 |
| `VSCodeAccent` | `#007ACC` | 当前 Tab、选中条、主按钮、状态栏 |

文字与状态 token：

| Token | Hex | 用途 |
| --- | --- | --- |
| `TextPrimary` | `#1E1E1E` | 标题、正文、关键数据 |
| `TextSecondary` | `#4F5B62` | 辅助说明、属性描述 |
| `TextMuted` | `#6E6E6E` | 弱状态、次要元信息 |
| `SelectedRow` | `#DCEBFA` | Explorer/表格选中行 |
| `Hover` | `#E8E8E8` | 行/按钮 hover |
| `Pressed` | `#D6D6D6` | 按下态 |
| `TableHeader` | `#F3F3F3` | 表头底色 |
| `DisabledBg` | `#F3F3F3` | 禁用控件底色 |
| `FocusRing` | `#007ACC` | 键盘焦点、当前控件描边 |

语义色单独使用，不算主题强调色：

| Token | Hex | 用途 |
| --- | --- | --- |
| `Success` | `#178A4A` | 已完成、通过、可继续 |
| `Warning` | `#C76F00` | 需检查、警告、待确认 |
| `Error` | `#D13438` | 阻塞、错误、不可继续 |

不得重新引入旧的自定义蓝底、营销页渐变、暖奶油模板、紫蓝渐变、过度圆角卡片、装饰性背景。

## 4. 统一排版与密度

字体：

| 用途 | 字号 |
| --- | --- |
| 顶部菜单、Explorer、Tab、表格正文 | 12 |
| 页面正文、字段标签 | 13 |
| 面板标题、区块标题 | 14 |
| 页面主标题 | 16 |

密度：

| 元素 | 规则 |
| --- | --- |
| Top Chrome | 高 36 |
| Tab | 高 36 |
| Status Bar | 高 24 |
| Explorer 行 | 高 26-28 |
| 表格行 | 高 28-32 |
| 普通按钮 | 高 28，水平 padding 12-16 |
| 状态短标 | 高 18-22，文案不超过 4 个汉字优先 |
| 表格单元格 | 水平 padding 8-12 |
| 面板内边距 | 20 或 24，不能随页面任意变化 |
| 图标点击区 | 32 起，Activity Bar 可为 48 |

排版要求：

- Explorer、Tab、表格、菜单使用紧凑行高，不做网页式大留白。
- 数字列、深度、单位、计数使用稳定列宽。
- 按钮、表格、列表、状态标必须对齐到同一列网格。
- 文案不得重叠、溢出或靠缩小到不可读来解决布局问题。
- 用户可见文案默认中文，必要技术符号和真实文件名除外。

## 5. 功能入口闭环

任何新增可见入口必须先分类，再设计落点。

功能状态：

| 状态 | 含义 | 设计规则 |
| --- | --- | --- |
| `已有` | 当前代码已有页面、route、服务或窗口 | 可以出现在主图，但要按真实能力表达 |
| `已有但需重排` | 能力存在但 UI 不符合当前布局 | 可重画布局，不改变业务边界 |
| `新增拟做` | 当前没有但本轮确认要做 | 必须补目标页面、面板、菜单或弹窗 |
| `未来能力` | 方向合理但 MVP 不做 | 默认隐藏，必要时弱化标注 |
| `精简隐藏` | 不该默认出现 | 移到高级、日志、方法实验室或删除 |
| `不做` | 超出当前产品边界 | 不进入设计稿 |

入口闭环必须回答：

1. 点击后去哪里？
2. 是页面、右侧面板、底部面板、菜单、弹窗，还是系统动作？
3. 当前版本是否已有实现？
4. 没有实现时，是本轮新增、未来能力，还是不展示？
5. 是否需要单独设计弹窗、面板、接口状态？
6. 是否覆盖默认、无数据、加载/运行、成功、警告、阻塞/错误、禁用、只读等状态？

没有闭环的入口不得进入主图。若设计中留下新增功能，必须同步留下对应窗口、面板、菜单、接口状态或明确隐藏决定。

## 6. 默认信息边界

默认主流程页只展示工程用户需要消费的信息。

允许默认展示：

- 工程结果、数据状态、质量问题、下一步动作。
- 当前点位、当前方案、当前输入来源。
- 预检摘要、问题摘要、结果对比摘要。

默认不展示：

- 方法运行器、注册表、草稿包、内部路径、trace、长日志。
- 开发过程记录、实现细节、调试对象名。
- 解释型大卡片、宣传式空话、假 dashboard 指标。

内部信息只允许进入高级、方法实验室、开发诊断、日志详情或用户主动展开的底部面板。

## 7. 设计交付关系

每个模块的设计交付分三层：

```text
模块功能设计文档 -> 真实 UI 图 -> 开发 handoff
```

规则：

- 文档负责讲清逻辑：页面目的、用户任务、入口、弹窗/面板、状态、错误、按钮启停、开发要求。
- UI 图负责讲清长相：默认页、必要弹窗、必要面板、关键空/错/成功状态。
- 开发 handoff 负责讲清落地边界：哪些已有、哪些新增、哪些不做、验收标准是什么。
- 不用一张大说明图承载全部逻辑；说明图只能作为内部检查，不作为主要设计交付物。
- 只有用户会真实看到、或开发需要明确布局的内容，才需要画成 Figma UI 图。

## 8. 设计工作流

每轮设计按以下顺序执行：

1. 确认本轮对象：只处理一个页面、一个区域或一组强相关弹窗。
2. 读取上下文：`AGENTS.md`、`design.md`、`Plan-total.md`、`plan.md`、相关 `docs/*spec.md`、已验收 Figma 参考、当前代码能力。
3. 先写模块功能设计文档：讲清当前对象、输入、主结果、状态/阻断、下一步、入口、状态和开发要求。
4. 列功能清单：标注 `已有 / 已有但需重排 / 新增拟做 / 未来能力 / 精简隐藏 / 不做`。
5. 定统一继承：确认哪些区域必须沿用 `01 Workbench shell` 或上一张已验收通用布局，并记录节点/截图/坐标证据。
6. 画真实 UI 图：默认页、必要弹窗、必要面板、关键状态；只画用户或开发真正需要看的界面。
7. 自检：中文化、对齐、溢出、密度、VSCode-like、入口闭环、默认结果可见、无内部开发词。
8. 安排 agents 审阅：Planning、UI/layout、Chinese user critique、Implementation/QA。
9. 修复 blocking 和必要 risk；未修复 blocking 时停止并汇报，不进入下一页。
10. 记录 review：文档路径、Figma 节点、截图、功能状态、入口闭环、残余风险。
11. 只有 review 关闭后，才允许写开发 handoff；未关闭前的文件标题和状态必须明确标为 `draft` 或 `blocked for review`。

## 9. Agent 审阅

每张主流程设计图完成后，必须安排独立审阅。没有审阅记录，不得进入代码实现。

每个设计 slice 必须写清：

- `design owner`
- `integration owner`
- 审阅角色
- 关闭结论

默认审阅角色：

| 角色 | 只负责检查 |
| --- | --- |
| Planning agent | 目标、范围、非目标、功能状态、入口闭环是否清楚 |
| UI/layout agent | 是否继承统一壳层，是否 VSCode-like，对齐/密度/色彩/字号是否一致 |
| Chinese user critique agent | 中文工程用户是否能直接理解，是否冗余，是否默认看到结果和下一步 |
| Implementation/QA agent | WinUI 是否可落地，现有能力是否被伪装成新能力，验收路径是否明确 |

审阅结论必须使用：

- `blocking`：阻止继续，必须修。
- `risk`：可继续但要记录影响、证据和后续检查。
- `nit`：小问题，不阻止继续。

关闭规则：

- 任意 `blocking` 未修复时，不得 handoff 给代码实现。
- 若默认屏幕看不到工程结果、状态或下一步，Chinese user critique 必须标为 `blocking`。
- `risk close` 必须由 `integration owner` 明确决定并记录理由。
- 审阅必须引用证据：Figma 节点、截图路径、文件路径、结构检查结果或 diff 范围。不得只写“看起来可以”。

## 10. 设计自检清单

交给用户审图前必须逐项检查：

- 通用壳层是否与基准节点一致。
- 颜色是否只使用本文 token 和必要语义色。
- 字体、字号、行高、间距是否稳定。
- Explorer、Tab、右侧面板、底部面板、状态栏是否统一。
- 用户可见文案是否中文，必要技术符号除外。
- 新增入口是否都有目标窗口、面板、接口状态或隐藏决定。
- 新增入口是否覆盖无数据、加载、成功、警告、错误、禁用状态。
- 功能是否按真实能力表达，没有把未来能力伪装成已完成。
- 默认屏幕是否先给工程结果、状态、下一步。
- 是否移除了内部调试和开发过程信息。
- 截图是否显示完整画板、目标页面、无遮挡，分辨率为 1920 x 1080。

## 11. 设计交付记录

每轮设计完成后，必须在对应 `docs/*review.md` 或 `process_logs/` 记录：

- 设计对象。
- Figma 节点 ID。
- 截图路径与分辨率。
- 功能状态表。
- 新增入口和目标窗口/面板/接口。
- 状态覆盖情况。
- 与统一壳层的一致性检查。
- agent 审阅结论。
- 未解决风险。

`design.md` 不记录具体页面历史。具体页面设计记录放到独立文档，例如：

- `docs/figma-interface-01-acceptance-review.md`
- `docs/figma-interface-03-data-import-review.md`
- 后续 `docs/figma-interface-04-data-check-review.md`
